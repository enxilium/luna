# Fast tools implementation and acceptance

The implementation keeps Qwen 27B, one MCP runtime, and native Pipecat tool execution. Both voice and typed conversations start the model immediately when a completed user turn reaches the pipeline. All spoken output originates in Qwen inference. Selective publication, paged results, and Pipecat's context summarizer remain. The earlier deterministic progress processor and its one-second TTS gate have been removed following the revised UX requirement.

## Turn flow

1. Before readiness, connect/discover configured catalogs and warm the model and TTS.
2. A final transcript or typed message passes through synchronous local tool selection directly to Qwen. Compatible tools and required companions are published from the local catalog; uncertain tasks retain `search_tools`. Idle summarization is preempted when necessary.
3. Qwen begins the same tool-enabled inference immediately. It is instructed to produce a brief acknowledgement before its first tool call for a new request. Sentence TTS consumes only Qwen's generated text; inference never waits for TTS or speaker delivery.
4. Qwen interprets the request and calls native Pipecat functions. The MCP runtime validates canonical arguments, allowlists, authorization and execution order, then returns actual results or explicit failures.
5. Oversized responses stay in session storage. Qwen reads necessary pages and generates the final answer; sentence TTS and the native output deliver it.
6. Native context summarization runs during idle time and is cancelled for a new user turn. Interruption cancels inference and normal playback through the existing pipeline.

An acknowledgement expresses intent only. It cannot authorize an action, confirm an effect, or substitute for the final service result. There is no separate acknowledgement pass, model or hard-coded sentence. Warm-up synthesis is silent and finishes before readiness.

## Reviewable stages

| Stage | Ownership | Behavior |
| --- | --- | --- |
| Instrumentation | `src/agent/services.py`, `src/audio/apple.py`, `scripts/benchmark_tools.py` | Inference start, actual outgoing function schemas, available token/cache counters, inference rounds, service durations, generated audio, native delivery/rendering, generated completion |
| Single-model speech | Both entry points and MCP instructions | Direct inference after the user turn, all speech generated by Qwen 27B, native interruption cancellation, engine warming before readiness |
| Narrow publication | `src/integrations/catalog.py`, `src/integrations/mcp.py` | Concise index, action compatibility, aliases, separate action clauses across services, best tool and companions, three-candidate fallback, six active tools, expanded 8 KB service-schema budget |
| Bounded data/context | MCP runtime and Pipecat aggregators | Equivalent text/structured data deduplicated, complete session response storage, explicit previews and bounded pages, native summary thresholds and cancellation |

Connection ownership, execution allowlists, original-schema validation, authorization, per-integration ordering, and cancellation remain in the MCP runtime. The typed Docs helper validates its arguments and transforms them into a canonically validated upstream request. Neither discovery nor authorization completion replays an action. Pagination installs a catalog atomically; repeated cursors fail instead of looping. Legacy list notifications and modern supported subscriptions request refresh. Explicitly missing services connect concurrently; an unrelated unavailable service cannot block an ordinary local search.

Tool descriptions and ordering remain stable for a selected set. Operation help is returned as data, including a stored reference when oversized; it does not rewrite definitions. Schema constraints are preserved. The existing single-oversize-schema exception remains. The byte budget includes expanded schemas and their OpenAI function wrappers, but excludes the fixed control tools.

Oversized results retain their status and explicitly say the preview is incomplete. `read_tool_result(result_id, offset=0, limit=4096)` returns text pages, total length and continuation offset. References expire at shutdown. Complete non-text MCP content is retained as serialized data; this paging tool is not a media renderer. Storage is session memory, so very large or prolonged sessions can still use substantial host memory.

Context thresholds are approximate message tokens: 6,000 to trigger, 1,000 summary tokens, and 12 recent messages preserved. Pending tool sequences can keep additional messages. This is a soft trigger, not a hard context cap. The summary prompt preserves preferences, exact identifiers, result references with length information, instruction scope and completed-action receipts. Summary generation waits until the terminal response reaches the assistant aggregator after TTS and output; it never runs alongside tool inference. New user input preempts idle summarization.

Clear local greetings omit tools and irrelevant service instructions for that inference, while retaining the session's selection for later requests. Requests involving services, uncertain requests, and active authorization retain normal discovery. Qwen uses temperature zero for consistent tool decisions. The fixed instruction requests one brief acknowledgement before tools and no repeated narration between calls. Whether Qwen follows that ordering is measured rather than assumed.

Playback identifiers must come from a successful Spotify response or explicit user input, including a Spotify URL. A guessed identifier produces a failure with search guidance and is never dispatched. This session metadata survives context summarization and clears on shutdown; canonical schema validation and authorization still apply.

Native input and output startup failures are permanent pipeline errors. Failed startup never declares the transport ready, and microphone capture starts only after readiness. Normal playback and silent native echo cancellation retain their separate engines.

## Reproduction

Use the pinned environment with Ollama and VoiceStudio running:

```sh
LUNA_LIVE_TESTS=1 uv run python -m unittest discover -s tests -q
uv run python -m scripts.benchmark_tools --turns 100 --compare-baseline --audible --first-utterance-only --output /tmp/luna-100-turns.json
uv run python -m scripts.benchmark_tools --cases multi_service,unsupported,large_result,summary_playback,auto_summary_playback,summary_result --audible --first-utterance-only --output /tmp/luna-stress.json
uv run python -m scripts.benchmark_tools --cases calendar --cold-model --audible --first-utterance-only --output /tmp/luna-cold-ready.json
uv run python -m scripts.benchmark_tools --cases explicit_playback --repeats 3 --audible --first-utterance-only --output /tmp/luna-explicit-playback.json
uv run python -m scripts.benchmark_tools --cases unsupported --repeats 3 --compare-baseline --audible --first-utterance-only --output /tmp/luna-unavailable-check.json
uv run python -m scripts.benchmark_tools --cases calendar,docs,spotify --repeats 2 --audible --first-utterance-only --output /tmp/luna-qwen-speech.json
```

The default schema snapshot is `scripts/fixtures/mcp-catalog.json`, captured on October 2. SHA256: `6e448d19596655b10bcdb58651272eb846a81b543e4e07c33fe6e5e64cefadd6`. Its original allowlists filter the snapshot before discovery; excluded Spotify tools never enter the fixture runtime. There are 65 allowed upstream tools across nine integrations plus the typed replacement helper. `--refresh-snapshot` reads the configured servers and updates the snapshot.

`baseline`, `selective`, and `bounded` are benchmark-only variants. The obsolete canned `progress` variant was removed. The frozen baseline archive contains the source already present before this implementation, including the user's existing changes. No production strategy switch or private executor was added. The default is the complete `bounded` variant with Qwen-generated speech.

The historical 100-turn matrix uses seed 20261003, eleven task families, 19 prompt variants, and randomized ordering within each eleven-task block. A randomized baseline pair is interleaved every four candidate turns: 100 candidate turns and 25 contemporaneous baseline turns. Each case creates a fresh conversation, except history cases seed 13 exchanges. Candidate `summary_playback` compacts history before the timed request; baseline retains its original history. Compaction time is reported separately. This tests cache changes between tasks and repeated identical requests; it is not a 100-turn continuous voice conversation. The focused suites separately test authorization, interruptions and pagination. `auto_summary_playback` waits for a native automatic idle summary in the same pipeline before a new playback request. `summary_result` retrieves a stored response after compaction without refetching or replaying an action.

The services and model are real; the MCP endpoint and effects are synthetic. Calendar ordering and exact time bounds, one exact edit followed by verification, search before one original-recording playback, and preference recall are checked. No external documents are edited and no Spotify playback is dispatched. The native transport opens output only, never the microphone.

The response clock starts when the typed final-transcript equivalent is submitted to the ready pipeline. STT and turn detection are outside it. First generated audio, first native scheduling/delivery, and first chunk render completion are separate. Render completion is a conservative upper bound on onset of native speaker output, not a calibrated acoustic microphone measurement. Only the first utterance is played during the matrix; all final replies are synthesized. Full spoken completion therefore is not measured in this mode. Service completion and final generated reply remain separately reported.

Available Ollama prompt/cache token counts come from the actual streaming usage records. Missing counters remain null. The runner writes raw rows and a companion summary using nearest-rank empirical p95; absent speaker output counts as infinity. Misses are not removed. The summary also reports service completions within ten seconds. Ten seconds is a performance target, not a destructive timeout or a reason to replay an unfinished operation.

## Current single-model validation

The revised entry points are tested with TTS deliberately blocked: inference starts before audio exists, and the only synthesized text is the simulated Qwen response. The benchmark now records `llm_start_seconds` and marks speech as originating from the main LLM. This measures pipeline inference start, not the server's first GPU operation. Current live measurements are recorded separately from the historical canned-speech experiment below.

The first six-case experiment passed 6/6 task checks. It covered a greeting, calendar, exact document replacement and verification, Spotify status, history-based playback, and explicit-URL playback. Inference started in 0.69–1.00 milliseconds. The greeting rendered at 1.48 seconds; all five service requests missed two seconds, with first speaker rendering at 7.79–18.13 seconds. Qwen omitted the requested acknowledgement in four of the five initial service responses.

A clearer instruction at the end of the fixed integration prompt still uses the same single tool-enabled Qwen inference. Its follow-up passed 6/6 task checks across two repetitions of three service tasks. Inference started in **0.64–1.73 milliseconds**. Qwen acknowledged the calendar request before tools, but still issued Docs and Spotify calls before speaking. The prompts, schemas and service ordering differ from the prior canned-progress matrix; these small experiments cannot establish a p95 promotion guarantee.

| Final instruction, native first speaker rendering | Repetition 1 | Repetition 2 | Median final tool result |
| --- | ---: | ---: | ---: |
| Calendar | 4.78 s | 1.65 s | 17.15 s |
| Document replacement and verification | 11.98 s | 8.78 s | 9.57 s |
| Spotify status | 6.02 s | 2.55 s | 3.07 s |

**The revised UX invariants are satisfied; the two-second first-speech target is not.** Five of six follow-up turns missed it. Summarized tools reduce context but do not eliminate Qwen prompt processing or guarantee text before structured arguments. An unchanged prefix can benefit from cache reuse, while service switches still change tools near the start of Ollama's rendered prompt. Tool completion also remains above ten seconds for some tasks. No second model, separate acknowledgement pass, automatic replay or canned fallback was introduced.

Evidence: [initial single-model experiment](benchmarks/qwen-speech-initial.json), [final-instruction follow-up](benchmarks/qwen-speech-followup.json), and their companion summaries. The two entry-point tests prove that blocked TTS cannot gate inference and that no `TTSSpeakFrame` injects a phrase. The final source hashes and test result are recorded separately in [single-model validation](benchmarks/qwen-speech-validation.json).

## Historical results: canned progress, now removed

**These measurements describe the superseded deterministic-progress implementation. Its sub-second speaker times cannot be claimed for the current Qwen-only flow.** The original raw observations and source hashes are retained as historical evidence. Reproduction commands above run the current single-model code rather than recreate that old progress stage.

The October 3 mixed matrix completed **100/100 candidate task checks**, with **zero two-second speaker misses**. First generated audio had a 0.136-second median and 0.926-second p95; native first-chunk render completion had a **0.176-second median and 0.971-second p95**. These include greetings without a progress label. The contemporaneous baseline completed 22/25 task checks and missed two seconds on all 25 turns; its speaker p95 was 36.224 seconds, with the missing-output failure retained in the denominator.

Candidate final tool results were slower in 3/20 pairs; generated replies were slower in 4/22. Aggregate improvement does not establish a guarantee for every task.

The separate ten-second completion target is **not met generally**. Of 82 candidate turns that executed service tools, 19 completed the requested service effects within ten seconds and 11 finished all tool results, including any retrieval, within ten seconds. Across those 82 turns, median final tool result was 14.90 seconds. Across all 91 turns with internal or service tool results it was 15.26 seconds, with p95 32.76 seconds. The median final generated reply across all 100 turns was 20.05 seconds, with p95 42.44 seconds.

The explicit-URL follow-up passed 3/3 checks; its slowest tool result was 10.40 seconds. Supplying an exact resource lets the model omit a lookup, but it does not guarantee ten seconds. It is a separate three-trial experiment, not part of the mixed matrix.

The median first outgoing schema was 4,523 bytes, with 6,398 bytes the largest first request in this matrix. The median task required three inference rounds. Synthetic MCP service execution took a median 5.3 milliseconds across 137 calls. This confirms that model prompt processing, argument generation and extra inference rounds dominate these measurements. Real remote-service latency and authorization can add further time. The implemented reductions retain canonical validation, verification reads, and correct recording selection; ten seconds is not enforced by cancelling or replaying service effects.

The mixed matrix exposed one unsupported-request regression: repeated search, reconnect and help rounds after a complete catalog returned no match. Candidate generated completion was 20.66 seconds median for that family, versus 8.20 seconds for its two baseline samples. The final runtime now reports that the complete loaded catalog found no compatible tool and that reconnecting cannot add capabilities. A subsequent interleaved check passed 3/3 candidate requests without service effects, using one search and two inference rounds. Candidate generated completion was 5.81 seconds median versus 5.11 seconds for that follow-up baseline. All candidate speaker renders were below 0.192 seconds. This result fixes the repeated-discovery regression; the small follow-up does not establish percentile completion guarantees.

The responsiveness and task-check gates passed in the fixture matrix. Aggregate completion improved against the contemporaneous baseline. **The full production promotion gate is not conclusively established:** per-family baseline samples are small, the unsupported family needed a post-matrix correction, and there is no continuous 100-turn microphone session or real remote-effect latency run. The ten-second target remains open. The code is implemented and verified locally; these observations should not be presented as an unconditional production performance guarantee.

Final stress checks passed 4/4: playback after explicit compaction, playback after genuine automatic idle compaction, retrieval after compaction without refetch/replay, and large-result paging. Speaker render times were below 0.190 seconds; generated completions were 23.97–26.95 seconds. A cold-model readiness check unloaded only the configured Qwen model, warmed it in 2.65 seconds, and rendered progress 0.192 seconds after the request. That calendar task completed its service effect in 15.22 seconds and generated reply in 23.00 seconds. VoiceStudio was already running; this is not a cold TTS restart or cold OS boot.

The baseline matrix's first multi-service turn encountered a native output startup failure: `player did not see an IO cycle`. It timed out at 180 seconds without speaker output or service calls. This row remains a failed task and latency miss. The cause of the native startup failure was not established. The final startup handling prevents claiming readiness after this error; forced-failure tests cover both adapters. The other baseline failures were a playback request that searched without playing, and a multi-service calendar call missing required ordering. Baseline completion medians exclude all three failed tasks.

The final check ran **73 tests, all passed**, including the opt-in real model/TTS authorization test. Compilation and diff-whitespace checks passed. Post-matrix changes clarify only the no-match result, accept explicitly supplied Spotify URLs and identifiers from successful Spotify responses, and handle native startup failures; they do not change the successful model prompt/schema or successful native output path measured in the matrix. The no-match correction has its own real-model comparison. Successful-output and compatibility paths have focused regression tests. Native summary limits remain soft: uninterrupted tool sequences can grow beyond the trigger until idle compaction becomes possible.
